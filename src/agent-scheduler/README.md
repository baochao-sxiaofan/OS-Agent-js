# 长期 Agent 调度器

公共入口：`os-agent-js/agent-scheduler`；仓库内从 `index.ts` 导入。
工厂 `createAgentScheduler()` 返回公共接口，内部队列、Map 和定时器不可直接访问。

本模块调度长期 ACB，独立于旧 `TaskScheduler` 和 TCB，不读取 Context，
不解释内部任务、不选择模型、不调用网络、不执行工具，也不决定请求级重试。
Context、模型和执行模块的组合由宿主负责，目前尚未接入桌面运行链路。

## 双 Map 与封存批次

每个 Agent 拥有以下内部记录：

1. Map1：已经发起、尚未结束的异步操作。
2. Map2：已经结束、尚未交付的结果。
3. 至多一个已入队或运行中的不可变批次。

Context 中“给客户发消息”是工作目标；查询联系方式、发送消息、写入标签才是
具体异步操作。尚未发起的计划步骤不能登记进 Map1。模型请求本身对应 RUNNING，
不作为使 Agent 阻塞的操作登记。

操作结束时，调度器同步将记录从 Map1 移入 Map2。成功、失败、取消、超时均为终态。
没有现存批次时：

- Map1 为空且 Map2 有结果：立即封存入队。
- Map1 非空且 Map2 有结果：首个结果到达后等待批处理窗口，默认 30 秒。
  后续结果不重置窗口，到期后封存部分结果。
- 两个 Map 都为空：不会发送空请求，除非收到外部事件或明确的继续运行意图。

封存同步完成“生成批次、替换 Map2、登记批次、入队”。后续回调只能写入新 Map2，
不能修改已经 READY 但尚未发送的批次。批次中的结果、事件和在途操作快照均冻结。
外部 Context 投影若也要冻结，应在对应模块内根据批次建立快照，不读取实时 Map2
追加输入。

每个 Agent 只有一个排队或运行中的批次。期间新结果和消息继续缓冲，本轮确认后
再检查下一批。批处理时间在运行期间到期时，只保留到期事实，不重复触发空转定时器。
不同 Agent 按先进先出共享运行额度，默认最多同时领取 4 个运行。

## 与 ACB 的边界

调度器通过 `AgentSchedulingHandle` 调用 ACB 状态接口，不能自行赋值 `state`。
实际规则由 ACB 模块校验，调度器负责根据收集状态选择转换时机：

- READY：存在一个尚未领取的封存批次。
- RUNNING：存在一个有效运行凭据；包括模型请求和调用方处理本轮返回的时间。
- BLOCKED：没有可发送批次，但仍在等待异步操作或部分结果批处理窗口。
- SLEEPING：没有在途操作、结果、消息、批次或继续运行意图。

Map1 非空时也可以 READY/RUNNING，因为模型可以先处理部分完成结果。
Context 内部 Task 的完成不直接决定 ACB 是否休眠。

`notify()` 的外部唤醒事件可以促成新批次；已有批次时只缓冲消息，不追加或并发执行。
即使发送方返回 `idle`，新消息仍会触发后续运行。消息正文需先登记在外部存储中。

## 调用顺序

1. 用 `createAgentControlBlock()` 创建 ACB，将其状态端口交给 `register()`。
2. 消息持久登记后调用 `notify(agentId, { eventId, eventRef })`。
3. 发送方在取得所需模型准入后调用 `takeNextRun()`；没有工作或额度时返回 `null`。
   `waitForReady(signal)` 可等待下一次可领取机会，多发送方仍须处理领取为空。
4. 发送方只使用 `run.batch` 中的固定输入，调用外部 Context/请求器接口。
5. 模型返回需执行操作时，先 `registerOperations(run, options[])`，再启动工具。
   执行模块拿到结果后先保存正文，再 `completeOperation(operation, outcome)`。
6. 批次结果已被吸收、本轮处理结束后，调用 `finishRun(run, 'continue' | 'idle')`。
   有新操作未结束时，即使传入 `idle` 也不能休眠。
7. 发送失败且尚未处理成功时，可由发送方显式 `returnRun(run)` 归还原批次。
   不自动发请求、不合并新结果；再次领取使用新 `runId`，旧凭据不能完成新一轮。
8. 全部工作结束并进入 SLEEPING 后，可以 `unregister(agentId)`。

发送方必须对每张运行凭据调用 `finishRun` 或 `returnRun`，包括异常路径。
请求重试应在已领取的同一批次上通过 model-requester 或宿主策略完成。
已经产生副作用的工具不得因为模型请求重试而重复启动；执行模块负责使用操作 ID
作为幂等键。`returnRun` 只保留交付输入，不会撤销外部操作或 Context 写入。

## 超时、边界与恢复范围

每个操作有独立的截止时间，默认 120 秒，可在登记时覆盖。到期后调度器登记
`timed_out` 并通过操作句柄的 AbortSignal 请求执行模块取消。本地停止等待不代表
远端停止执行；迟到和重复回调返回 `false`，执行模块仍负责远端结果对账。
批处理定时器只影响结果交付，不能替代操作截止时间。这里不轮询外部 API；
需要主动查询外部作业时，由执行模块查询并在终态回调。

操作 ID 由调度器生成，不复用。结果已进入批次或已消费后，重复回调也无法再次投递。
外部事件使用有界近期去重缓存，同时保留对当前批次和待处理事件的去重；
宿主仍需负责超出缓存范围的持久事件去重。

每个 Agent 默认最多缓冲 256 个操作（含批次中未确认的结果）和 256 条消息。
达到上限时抛错，调用方须保留未被接收的输入；不得静默丢弃。
本实现是单进程内存调度器，同步操作保证回调交错下的原子性，不提供跨进程事务、
进程崩溃恢复或持久队列。注册时拒绝缺少调度记录的 RUNNING/BLOCKED 实例。
后续持久化时必须将批次、Map 转移和队列登记纳入同一事务或可靠投递机制。

状态端口只交给可信调度器使用；同一 ACB 不得注册到多个调度器，其他调用方也不能
在运行期间修改状态。端口必须同步执行且不能重入调度器。

完整本地读取示例：`npm run demo:agent-scheduler`。
